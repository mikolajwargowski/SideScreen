# ADB checklist stream reset diagnosis

Date: 2026-08-17

## Summary

The USB readiness checklist can open a short-lived TCP connection to the same
port used by the real SideScreen Flow stream. The Mac host currently keeps a
single active client connection. Every new probe connection can therefore
cancel the active stream connection, which makes Android appear to connect for
a moment and then disconnect again.

Observed symptom:

- Android showed `Mac Server Running` as green, then briefly red, in a loop.
- The loop repeated roughly every 2 seconds.
- Pressing `Connect` started a stream for a short moment and then returned to
  disconnected state.

## Root Cause

The Android USB checklist verifies the Mac server by connecting to
`127.0.0.1:<port>` through `adb reverse`. The default stream port is `54321`.

That health check is not isolated from the real streaming protocol:

1. Android opens a probe socket to `127.0.0.1:54321`.
2. ADB forwards it to the Mac host.
3. The Mac host accepts it as a normal incoming stream client.
4. The host cancels the previous client because `StreamingServer` tracks one
   active `NWConnection`.
5. The probe closes or resets because it is only trying to test reachability.
6. The real stream is gone, and the UI falls back to disconnected.

This repeats as long as the checklist is active.

## Evidence From Live Diagnosis

`adb reverse` was present and correct:

```text
UsbFfs tcp:54321 tcp:54321
```

The Mac host was listening on the stream port:

```text
SideScree ... TCP *:54321 (LISTEN)
```

While the Android app was open on the checklist screen, `lsof` repeatedly showed
short-lived ADB loopback connections:

```text
adb        ... TCP 127.0.0.1:<ephemeral>->127.0.0.1:54321 (FIN_WAIT_2)
SideScree  ... TCP 127.0.0.1:54321->127.0.0.1:<ephemeral> (CLOSE_WAIT)
```

After force-stopping the Android app:

```bash
adb shell am force-stop com.sidescreen.app.dev
```

the repeated ADB connections stopped. The only remaining socket was the Mac
listener on `*:54321`. That confirms the loop was generated by the Android app,
not by ADB itself or by the Mac server restarting.

The Android private diagnostic log also showed repeated fresh stream startups:

```text
SC: Connected to 127.0.0.1:54321
SC: Display config: 2800x1752 @ 0°, h=false, v=false
SC: First video frame: ...
```

Those repeated first-frame entries indicate the stream can start successfully,
but another connection keeps replacing it.

## Why It Worked Before And Failed After Restart

The Mac restart did not remove `adb reverse`; it was still configured correctly.
The likely state change was the Android app returning to an idle USB readiness
screen after the Mac host was restarted.

Before the restart, the checklist may have been inactive because:

- the stream was already connected, so checklist updates were skipped;
- the app was on the Wireless tab, where checklist polling is paused;
- the app had been freshly connected after a state transition that stopped the
  checklist;
- or the tablet app was not left running on the USB checklist screen.

After the restart, the Mac host came back and the tablet app still had a valid
`adb reverse` path. The USB checklist therefore resumed probing `54321` every
2 seconds. Because `54321` is also the streaming port and the host is
single-client, each probe could evict the real stream.

This makes the failure look like "the server is running but Connect drops after
2 seconds", even though the underlying stream, decoder, and reverse forwarding
are all capable of working.

## Fix

The Android client must stop checklist polling before opening the real stream
connection and give any in-flight probe a brief time window to finish.

The USB connect flow now:

1. stops checklist updates;
2. disables the Connect button;
3. waits briefly;
4. opens the real stream connection.

Wireless mode already pauses the USB checklist while the Wireless tab is active,
because USB loopback probes can also fight a wireless session for the Mac host's
single-client slot.

## Operational Workaround

If the issue appears on an installed build that does not contain this fix:

```bash
adb shell am force-stop com.sidescreen.app.dev
adb reverse --remove-all
adb reverse tcp:54321 tcp:54321
```

Then reopen SideScreen Flow on the tablet and connect again.

This workaround removes the active polling loop, but the code fix is still
needed so the checklist cannot race the stream after future restarts.
